What was there before

Declared, and never written

entry, rule and rule_section had existed in the schema for some time. All three were reported not wired by the bundler: the reach builder resolved 2,962 of 3,050 rules in 2.7 seconds, wrote its answer to disk, and nothing read it. Every regulation screen in the app was drawing from an empty table.

So no resolver, tributary walker or extent engine needed writing. The work was deciding what shape reaches the client, and wiring four tables.

The shape

Say it once and point at it

A regulation applies to a stretch of river, and a stretch is many sections. A river with one closure repeats that closure down every section of its length. Counted on the province: 583,654 sections carry a rule, and between them they hold 1,905 distinct sets. One set is shared by 104,185 sections.

The test that matters

Not a row count — a row count agrees with itself. Ground truth is the reach builder's own 1,720,243 bindings; expand the sets from the built bundle and every one comes back. None missing, none invented. A compression that drops one binding drops a closure on a real river; one that invents a binding closes water that is open. Both are invisible to a count. Kept as a slow test.

Both new tables are WITHOUT ROWID and keyed the way they are read, so their primary keys are their indexes. The one direction with no key — "which sections does this rule cover" — is a question the app never asks: a rule is reached from a section, never swept for.

Correction · the plan had this wrong

Two facts, not one column

The plan kept the old (scope_kind, scope_id) column and had the client unioning section, mu, area and trib bindings per section — which is the front-end computation the whole design exists to avoid. It also conflated two things that are orthogonal.

And the set count

The plan said 1,641. Re-measured against the current build: 1,656 without provenance, 1,905 with via in the set's identity. Carrying it costs 249 sets and 0.3 MB — and it is not decoration. The tributary sweep is the corpus, and it is the part that can be wrong over thousands of kilometres at once: on the Kootenay, a watershed-prefix shortcut adds 3,205 km of water joining below the regulated reach. A row that cannot say how it got here cannot be audited by anyone.

The rules menu

A river as its regimes, not the atlas's cuts

The atlas splits a river at confluences, lake outlets, gauge matches and a 25 km length cap. None of those is a reason a regulation changes — so the Fraser rendered 248 rows, every one reading the same, and the stretch where the rules actually change was indistinguishable from its neighbours.

The bundle had already decided which sections answer identically. The menu groups on it.

Execution

Six steps, and the gate each had to pass

  1. A scope on every binding

    The reach builder now records which sections arrived by the tributary walk, taken at the one line where the two sets are still apart.

    same 2,962 rules bind · same 1,720,243 rows · same digest b0d11723f0ab1368

  2. Intern the sets

    Group each section's (entry, rule, via) triples, sort, intern. Sorted before interning so the same corpus always yields the same ids — numbering that moved between builds would diff as though every section had changed.

    583,654 sections · 1,905 sets · 6,622 rows

  3. Write entry and rule

    Straight from the curated entries, keyed on the pair.

    1,393 entries · 3,050 rules · 88 flagged uncertain

  4. Write section_ruleset and ruleset

    Nothing on the tile — verified: no layer references rule data.

    bundle 49.8 → 62.5 MB, not 121

  5. Resolve in the client, in one place

    One query in the data layer, one grouping function in @app/core, used by every surface that lists a water.

    563 app tests · layer boundaries clean

  6. Regenerate the fixture from the real shape

    The fixture interns exactly as the pipeline does. Hand-writing it is how 1,785 rows of a band the pipeline never emitted once got in and three test files asserted on them.

    every table present · all four columns

Found along the way

Three bugs, two of them latent

Stretches drawn out of order

SECTIONS_FOR_ITEM said ORDER BY section_id, under a comment claiming ids sort mouth-to-source "because the measure is distance up the blue line". The id is {blue_line}:{measure} and the column is TEXT — so …:122095 sorted before …:9942. The sheet drew a river's stretches out of order while saying they were in order. Split and cast now, blue line first: an item is not one line — "Fraser River" spans 151 of them.

A viewport that would have crashed

The rule lookup bound every section id in one statement, while the gauge queries beside it chunk at 400–500 under a comment naming SQLite's 999-parameter ceiling. It never bit because the table was empty — every lookup returned nothing, so the query was never asked a big question. Real rules turn that into a crash on a zoomed-in map.

The test asserts on our side of the line: no statement binds more than 999. The first version simply issued a 2,500-section query and passed — this build has the newer 32,766 limit, so it proved nothing.

Pre-existing, and not touched

Slow tests are deselected by default and have been red without anyone noticing. Two assert province thresholds that went stale when the leaf prune landed (the Fraser's tributary set is 385,140, against an assertion of > 400,000). Two more are a genuine disagreement between tributaries_of_reach and lake_tributaries — the reach walk returns fewer sections, which is the under-closing direction. Neither is mine and neither is guessed at: changing an assertion to match current behaviour without knowing whether the behaviour is right is how a real defect gets ratified.

Not done

What is still open

The 110 unclassified and 67 ambiguous_cut diagnostics are written to disk and belong in a curation review queue, not in the bundle — they are curator-facing, not user-facing. ItemRegs.area (zone and province-wide tiers) is still empty, which matches a corpus with no zone rules in it yet. The verbatim clause offsets the panel would use to highlight the parsed words are still a parser output the bundle does not carry, so it highlights nothing rather than the wrong words.

And the pairing between bundle and tiles is now load-bearing for correctness rather than just for colour: the bundle stamps the reach digest and the atlas it was resolved against, so a mismatched pair is detectable instead of silently short a closure.
