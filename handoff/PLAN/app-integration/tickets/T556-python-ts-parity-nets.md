Source: data pipeline review 2026-11-09 (owner-led; 14 areas + a gap check, every finding re-read against the code and release data by a second reviewer). Rank 12 of 17; highest severity 3 of 5.

Line numbers are the reviewers' and may be off by a few; "Second opinion" is what the verifier corrected. Fixes are proposals: re-read the code before building.

## Today
### 1. Three producers of salmon answers (Python release, Python local feed, TS worker feed) with no parity net left between Python and the TS port
Severity 3, divergence, partly, reaches an angler; area dfo-salmon.
- Evidence: TS ports of fetch/parse/untangle/locations(fingerprint)/entries/header/quota/typed/salmon live in app/workers/feeds/src/dfo/*.ts beside pipeline/regs/dfo_salmon/*.py + pipeline/deliver/salmon.py. test/dfo.scenario.ts:2-5: the byte-parity runners were deleted (T431/T350). What remains: wording only (dfo.wording.test.ts:30, `skipIf` no .venv), and dfo.dates.test.ts:46 compares the TS reader with a TS copy of the Python reader, one way. Robust mode differs on purpose (live.ts:15-20; dates.ts vs dates.py). The app's composeChain golden (core/src/salmonFeed.golden.ts) is written by pipeline/tests/test_dfo_live.py:24 from the PYTHON feed, while production serves the TS feed.
- Example: Date shapes the Python reader refuses and the worker reads (dfo.dates.test.ts:58-100: 'Aug 2 To Aug 31', '1 Oct to 31 Dec', 'Oct 1st to Dec 31st'): the release file makes the row an unparsed advisory, the live feed a dated rule. Same page, two answers, chosen by whether the device has a feed capture (pickSalmon).
- Second opinion: The facts hold: no test pins the TS parse/typed/fingerprint/calendar to the Python, and the two date readers differ on purpose. Overstated: dropping byte parity was a recorded owner decision (T350/T431), not an oversight, so 'no net left' is a known trade. The unrecorded part is the consequence: the same page can read as a dated rule in the live feed and as unparsed in the release file, and fingerprints (which the review queue and the worker must agree on) have no cross-language pin. I did not re-run the Python reader on those shapes; I relied on the test's own title and cases.
- Proposed fix: One cheap pin instead of byte parity: a committed vector file generated by Python over the fixture pages (per row: fingerprint, typed rules, per-location calendar runs) that the worker test must reproduce, with the known robust-mode differences listed explicitly. Port the robust date reader back to Python (or generate both from one table) so the release and the feed read a date cell the same way.

### 2. DFO page parser and location fingerprint exist in Python and TypeScript with no parity test since T431
Severity 3, divergence, confirmed, reaches an angler; area cross-duplicates.
- Evidence: Curated DFO entries carry fingerprints minted by Python: pipeline/regs/dfo_salmon/locations.py:78-99 (normalize, fingerprint) over parse.py/untangle.py. The live worker re-derives them in TS: app/workers/feeds/src/dfo/locations.ts:5-38 (same synonym table, stopwords, sha256), parse.ts, untangle.ts, and binds by them in entries.ts:57-60 (byFingerprint). app/workers/feeds/test/dfo.scenario.ts:1-4 states the TS-vs-Python parity runners were removed (T431, after T350). Only wording has a Python check left (test/dfo.wording.test.ts:30). names.ts:1-17 (port of names.key) has no shared case table either.
- Example: Add a synonym to _SYNONYMS in locations.py (e.g. 'br.' -> 'bridge') and re-queue: every curated fingerprint for text with 'br.' changes, the worker still computes the old one, and those rows fall to unplaced.json.
- Second opinion: 'Nothing fails at test time' is slightly too strong: dfo.worker.test.ts checks verdicts on named fixture locations against Python-minted fixture entries, so a gross TS-side break would fail. A narrow one-sided synonym edit would not. At run time the miss is not silent: the worker raises dfo-drift / dfo-new notices and writes unplaced.json.
- Proposed fix: A small shared vector file (like search_key_cases.json): for the 9 committed fixture pages, Python writes location fingerprints + water ids + names.key cases; a worker test and a pytest both assert them. Cheap, no byte-parity of the whole feed needed.

### 3. Feed formats live at one unversioned path with exact-match checks; a bump silently strands older apps and has already broken the worker once
Severity 3, fragility, partly, reaches an angler; area feeds-worker.
- Evidence: The format string is hand-copied: dfo-feed/3 in workers/feeds/src/dfo/live.ts:42, packages/core/src/salmonFeed.ts:27 and pipeline/regs/dfo_salmon/live.py:73; inseason-links/3 in pipeline/regs/inseason/publish.py:42, core/src/inseason.ts:25 and the worker's matchedWaters. App: data/src/feed/salmon.ts:65-71, a 200 body that is not dfo-feed/3 returns the capture with no reportFailure; data/src/feed/inseason.ts:52 likewise. minAppVersion gates releases only (update/service.ts:260). The gauge client (feed/http.ts) has no format check.
- Example: Staging status.json, inseason.lastError at 2026-11-09T22:54:30Z: 'in-season: matches.json is inseason-links/3, not inseason-links/2'. The pipeline published /3 before the worker was redeployed.
- Second opinion: Overstated on duplication: the worker's in-season links format is the app's own constant, not a hand copy, and unreadable in-season links are reported. Each side is pinned to the literal by its own test (test_dfo_live.py:79, test_inseason_publish.py:43, events.test.ts:305-307) but nothing ties Python to TS. What stands: one unversioned key, no minAppVersion on feeds, and a wrong-format DFO index is silent in the app. The past worker break is corroborated by the comment at inseason.ts:386-387; I did not re-read the staging status.
- Proposed fix: Publish a bumped format at a versioned key (feeds/dfo/v4/index.json) and keep writing the old one for a while, or add minAppVersion to the feed index and reuse the release gate's update prompt. Report an unreadable format. Add one test that pins the three constants together.

### 4. The remaining Python-vs-worker parity tests skip without a word when the repo venv is missing
Severity 2, missing-check, confirmed; area cross-duplicates. Related ticket: T543 (related; the silent skip is not in its scope).
- Evidence: app/workers/feeds/test/gauges.parity.test.ts:16, gauges.skill.test.ts:126 and dfo.wording.test.ts:30 are all `describe.skipIf(!existsSync(PY))`. The app side got a strict switch (scripts/test-full.sh:25-28, REGS_STORE_REQUIRED=1, T432); the worker suites have none. deploy/staging/feeds.sh runs the same vitest command before a deploy.
- Example: A fresh clone or a moved .venv: `npx vitest run` in app/workers/feeds reports green with the gauge feed parity, score parity and wording parity all skipped, and the worker deploys.
- Second opinion: Lower odds than implied: app-ci.yml:31-35 creates .venv before the worker suites, and the owner's Mac (the only place feeds.sh runs) has one. The gap only bites on a clone or worktree without .venv, where feeds.sh would deploy with all three parity suites skipped.
- Proposed fix: An env switch (e.g. PARITY_REQUIRED=1) that turns the three skips into failures; set it in feeds.sh and app-ci.yml.
