## Today
### 1. A catalogue entry's `matched` id that the atlas no longer has is dropped without a word at build time
Severity 3, wrong-or-missing-data, confirmed, reaches an angler; area atlas.
- Evidence: pipeline/atlas/reach/covered.py:74-82 `covered_ids` returns `[i for i in entry['matched'] if i in registry]`. The reach build calls it at pipeline/atlas/reach/build.py:140-141 and 443 and emits no diagnostic for a filtered id. Absorbed ids are mapped first (regs/parsing/io.py:312-314), but an id that is simply gone (a wsc: to gnis: flip, a blk: side-channel re-key, a pruned water) is not. The only signal is the review app's `binds_nothing` (regs/review/precheck.py:110-112), which fires only when every id is gone and is not a build gate. Steelhead (reach/steelhead.py:329) and DFO places (reach/dfo_salmon.py:81-83) raise on the same condition.
- Example: Today 0 of about 1,470 distinct item ids in data/curated/regulations/synopsis/*.json are missing from data/generated/atlas/full/registry.json (checked), so a hard stop would cost nothing now.
- Second opinion: Stands. Two notes: the docstring shows the filter is deliberate (so a gone id cannot widen scope), the missing part is the report. Manual resync tools exist (regs/parsing/backfill_matched.py and the prune/backfill procedure) but nothing runs them or gates on them. The steelhead citation (steelhead.py:329) is about the steelhead list failing to resolve, a looser parallel than the DFO one. I did not re-count the finder's '0 of 1,470 missing today'.
- Proposed fix: In the reach run, stop (or at least write a `matched_gone` diagnostic that the release check counts) when any `matched` id is neither an item nor an alias of this registry, as the steelhead and DFO paths already do. Have promote's dry run list the curated ids the candidate registry lacks.

### 2. entry_scope returns 'no clip' when the row's scope fails or is empty, and report.scope_unresolved is read by nothing
Severity 3, fragility, partly, reaches an angler; area reach-binding.
- Evidence: pipeline/atlas/reach/build.py:1132 `return (out or None), failed`. When every scope extent fails, or resolves to zero sections, clip is None and build_reach (:472 `if clip is not None`) applies no clip, so each rule's `whole` binds the whole matched water. The docstring at :1114-1116 promises the opposite ('never treated as do not clip, which would silently widen a regional row to the entire river'). A zero-section scope is not even added to `failed`. A partly failed scope silently narrows to the extents that resolved. `scope_unresolved` is written at build.py:148 and models.py:153; grep finds no reader (cli.py does not print it, nothing gates on it).
- Example: Live report.json scope_unresolved = ['r5:chipmunk_lake@6-1', 'r5:toms_lake@6-1']. Both are pointer rows with no rules and `matched` null, so nothing is widened today. The hazard is latent for the first row with a failed scope cut that does have rules.
- Second opinion: "Read by nothing" is too strong: the review app computes the same failure itself and returns it per entry (curation-review/backend/reuse.py:720 and :749, pinned by tests/test_review_reaches.py:303), so a curator opening that entry sees it. What nothing reads is the run's report field, and nothing stops or flags the run. The widening is latent, as the finder said: no live row is affected. The exposure is real though (117 scoped rows with rules), and the failure direction is a wrong answer in both directions (a closure of one stretch spreads to the whole river, or an exemption does).
- Proposed fix: When scope extents exist and any fails or the union is empty, mark every rule of the entry unresolved (scope_unresolved) instead of unclipped. Make the CLI print scope_unresolved and exit non-zero when a listed entry has rules.

### 3. Closure pieces the reach cannot place are withheld with no gate and nothing shipped (Noons Creek, Seymour River)
Severity 3, wrong-or-missing-data, partly, reaches an angler; area reach-binding.
- Evidence: pipeline/atlas/reach/classify.py:32 `STRADDLERS_INCLUDED_FOR = frozenset()` and :237-246: an `unclassified` piece is never bound, only written as a diagnostic. pipeline/atlas/reach/build.py:1226 `STRADDLE_GATE_REASONS` holds only straddles_the_cut / joins_a_straddling_braid, so extent.py:669-671 reasons (meets_the_line_at_the_cut, leaves_bc_unjoined, flows_to_the_sea_unjoined) pass the run. pipeline/deliver/bundle/rules/diagnostics.py:8-27 ships only `ambiguous_cut`; no other diagnostic kind reaches the bundle or app. Also build.py:155 writes `scope_unclassified` without a `reasons` key, so the gate loop at :1235 can never fire for that kind.
- Example: data/generated/reaches/full/rule_diagnostic.jsonl:307 r2:noons_creek@2-8 noons_creek.r1 ("No Fishing upstream of railway bridge") pieces ["-2200000392:0"] reason flows_to_the_sea_unjoined, included false. Line 338: seymour_river.r1 ("No Fishing downstream of Seymour Lake") piece -2000000390:0. Both pieces are sections of the matched item in registry.json (gnis:23366 ref_ids include blk:-2200000392) and are in neither tidal.jsonl nor outside_bc.jsonl.
- Second opinion: "Nobody is told" is overstated for the rule-level case: the review app does surface it. pipeline/regs/review/precheck.py:118-123 turns each unclassified diagnostic into an unplaced_pieces finding, severity.py:38 ranks it high. So the owner's review queue lists both waters; what is missing is a run gate and any trace in the bundle/app. The finder under-stated the scope_unclassified part: that kind is read by neither the gate (no reasons key) nor the review queue (runfacts.py:68 skips it), so a piece lost at entry-scope level is truly invisible. Live count of scope_unclassified is 0, so that half is latent. Whether the two pieces actually lie inside the closed stretch was not established by the finder or by me.
- Proposed fix: Make every unclassified reason either gate the run or be owner-accepted per piece in a curated allow-list (accepted pieces listed in report.json). Ship unplaced pieces to the bundle as a 'check' flag on the section, like not_yet_mapped. Add `reasons` to the scope_unclassified payload so the gate can see it.

### 4. DFO salmon placement skips the tidal subtraction and discards every diagnostic that provincial rules ship
Severity 3, divergence, partly, reaches an angler; area reach-binding.
- Evidence: pipeline/atlas/reach/dfo_salmon.py:71 calls `build_reach(entry, rules[0], registry, graph, outside=outside, regional=False)`: no `tidal=`, no `owned=`, and the diagnostics are dropped (`binding, _`). build.py:425-432 documents that tidal=None 'takes nothing out' and owned=None makes 'every joining water go with the cut'. Provincial rules get both (build.py:164-166) and their ambiguous-cut picks ship (tables.py:302-305). pipeline/deliver/salmon.py:72 keeps a no-region shard 'x' for tidal sections ('the map reads it'). T449 (regs/dfo_salmon/entries.py:216-220) says tidal water is 'off the freshwater map'. I did not trace how the app renders a salmon chain on a tidal section.
- Example: Live run data/generated/reaches/full: 18 of 187 bound DFO locations bind sections listed in tidal.jsonl (101 tidal sections in all). 1:chemainus-river:whole has 16 of its 24 sections tidal; 1:campbell-river:downstream-of-the-confluence-with has 5 of 8; 2:default:areas-28-29 has 60.
- Second opinion: The code divergence and the numbers are confirmed. The user-visible effect is not: neither the finder nor I traced what the app shows for a salmon chain on a tidal section. app/packages/core/src/salmon.ts:1027 gives a tidal page its own tabs with salmonGear null, and deliver/salmon.py:73 says only the map reads the no-region shard, so the page side may already be guarded and only map colouring is in question. No ruling in RULINGS.md says DFO rows keep or lose tidal water (K7 covers provincial rules only), so this may need an owner decision, not just a fix. "Discards every diagnostic" is right, but DFO has its own hard stops the finder did not credit: stale_bindings and dead_pieces both fail the build (dfo_salmon.py:82-88). The missing owned= (confluence joining water always goes with the cut for DFO) is a second real difference the finder mentioned only in passing.
- Proposed fix: Pass the run's tidal map to the DFO placement (cli.py:126 already holds result.tidal), or record an owner ruling that DFO rows keep tidal water. Write the DFO diagnostics beside dfo_salmon.jsonl.gz and surface ambiguous_cut and unclassified in the DFO review.

### 5. Which water a book row means is stored twice; backfill_matched overwrites the entry's copy with the matcher's, with no guard and no parity check
Severity 3, divergence, partly, reaches an angler; area regs-parse.
- Evidence: Site 1: `matched` on each entry in data/curated/regulations/synopsis/region-*.json, the copy the reach build and bundle read, written by ingest (ingest_catalogue.py:98-99) and by the review app (pipeline/atlas/reach/covered.py:12-16 says so). Site 2: data/curated/regulations/book_name_links.json, read by the matcher via batch_exporter.py:289-290, backfill_matched.py:84 and review tools. backfill_matched.py:65-69 sets `matched` to the matcher's answer wherever they differ, for every entry, without the ingest ledger or marks. pipeline/tests/test_backfill_matched.py has four fixture tests only; I found no test or gate that the two agree on the real corpus.
- Example: Not measured: the dry run needs the 124 MB registry, outside this pass's limits. `backfill_matched --dry-run` prints the entries it would restamp; any line it prints today is a row where the two homes disagree.
- Second opinion: The framing 'two homes that each take owner edits' is not shown. By design book_name_links.json is the input and entry.matched is the stamped output; I found no review-app code that edits matched specifically (covered.py:16 says 'or the review app', but no such writer exists), so 'an owner fix in the review app is reverted' is unproven. What is real: matched is a cache of matcher output that goes stale after a name-link or registry change until someone runs the backfill, the backfill restamps everything unconditionally, and no check lists rows where the two disagree. The finder did not measure any disagreement, and neither did I (needs the 124 MB registry). Treat as a missing parity check, not a known wrong binding.
- Proposed fix: Pick one home. Simplest: keep `matched` on the entry as the truth; make backfill report-only by default (write only empty `matched`, or only ids named on the command line), and add a build-status check that lists rows where matcher and entry disagree.

### 7. Matcher's `unresolved_ids` has no consumer: curated override ids that hit no registry item are dropped silently
Severity 2, wrong-or-missing-data, confirmed, reaches an angler; area reach-binding.
- Evidence: pipeline/regs/matching/matcher.py:366-377: typed ids with no id_index hit go to `unresolved_ids` 'for the RESOLVER (Goal 2)' (docstring :14-17, :60-61). A repo-wide grep finds the field written only in matcher.py (:60, :377, :384) and read nowhere. batch_exporter.py:186 reads only `m.also`. When at least one id resolves, status is `override` and the rest vanish with no report.
- Example: book_name_links.json 'OKANAGAN RIVER OXBOWS' (MU 8-1) pins 40 wbk polygons and 27 wsc oxbow channels. 26 of the 27 wsc codes (e.g. wsc:300-432687-461418) appear nowhere in data/generated/atlas/full/registry.json. Entry r8:okanagan_river_oxbows@8-1 `matched` holds only the 40 wbk ids. Its one rule is 'EXEMPT from the spring closure'. It was the only override with dead ids, out of 499.
- Second opinion: Nothing material overstated; the 26-of-27 count reproduces. Two notes. The one wsc id that does exist in the registry is also not in the entry's `matched` (all 40 are wbk), so the loss is slightly wider than stated or `matched` was set by another path; I did not trace which. The "only override with dead ids, out of 499" claim I did not re-check. Impact is restrictive (nameless channels stay spring-closed) and small today; the defect is the silent partial resolution.
- Proposed fix: Have the matcher or ingest report every unresolved typed id (a count plus list in the ingest ledger) and fail when an override resolves only in part without an explicit `expected_unresolved` note. Delete the dead 'resolver will bind these' contract, or build it.

### 8. The reach promotion gate (binding_diff) does not compare DFO placements, diagnostics, tidal or steelhead tables
Severity 2, missing-check, partly, reaches an angler; area reach-binding.
- Evidence: pipeline/atlas/reach/binding_diff.py:12-15 compares only rule_section, rule_unresolved and licensing_section. grep for dfo_salmon / rule_diagnostic / tidal / steelhead_presence in binding_diff.py and diff.py returns 0 hits. Yet cli.py:124-128 places the DFO locations with the same build_reach, cuts and walk. dfo_salmon.jsonl.gz is deliberately 'OUTSIDE the rules' digest' (reach/dfo_salmon.py:8-10), so the run digest does not move either.
- Example: A split fix that moves a cut used by a DFO location (187 bound locations in the live run, e.g. 1:campbell-river:from-a-fishing-boundary-sign-at-th) changes its sections with a clean binding diff and an unchanged digest. A new `unclassified` piece or a changed ambiguous-cut pick is equally invisible.
- Second opinion: Confirmed for DFO placements and for the diagnostics (a new unclassified piece or a changed ambiguous-cut pick does not show). Overstated for tidal and outside_bc: zone rules bind every freshwater section, so a section gaining or losing tidal/outside status moves the region-base rule_section rows and does show in the diff (the two unplaced pieces above appear in 92 z2 rows, for example). The same holds for a moved cut, which changes section ids. So the unseen cases are narrower: a DFO-only walk or extent change on unchanged sections, diagnostics, and steelhead_presence. tests/test_tidal_pinned.py also pins a few tidal waters.
- Proposed fix: Extend binding_diff to diff dfo_salmon.jsonl.gz (sections per location_id), tidal.jsonl, outside_bc.jsonl and the rule_diagnostic kinds unclassified and ambiguous_cut (used measure), with the same exit status.
