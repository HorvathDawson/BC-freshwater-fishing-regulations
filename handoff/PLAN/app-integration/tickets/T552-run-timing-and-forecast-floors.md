## Today
### 1. Run-timing build has no floor check: an upstream column or page change can publish an empty or collapsed feed
Severity 4, missing-check, confirmed, reaches an angler; area forecast-runtiming.
- Evidence: pipeline/runtiming/parse.py:158-172 reads NuSEDS with row.get(...) and `continue`s on any row whose SPECIES / FWA_WATERSHED_CDE / GFE_ID / ANALYSIS_YR is missing; a renamed column skips every row with no error. read_sites (parse.py:222-231) likewise skips rows on KeyError. pipeline/runtiming/feed/build.py:281-320 `check` tests only internal consistency (hashes, profile indexes, counts ascending). feeds-runtiming.yml step 7 (line 163) gates on CHANGED only, and diff.py:38-52 reports runs dropped but never refuses.
- Example: If DFO renames SPECIES to SPECIES_NAME, dfo_records returns 0 records; diff reports ~4,944 dropped, changed=true, and with upload=true the index is replaced. During a release upload the pointer then flips to it.
- Second opinion: Narrower trigger than stated: since T485 step 2 a changed upstream format only arrives on a refresh=true run or when no copy is kept; release-triggered runs read the kept copy. But one thing is worse than reported: the refresh branch tars and uploads the fresh fetch as the kept copy (workflow :138-140) BEFORE parse and build run, so a broken download becomes the copy every later release-triggered run builds from, until someone refreshes again.
- Proposed fix: In parse or build, refuse when required columns are absent from the CSV header, and refuse a publish when PSF runs, DFO records or bound sections fall more than a set share (say 10%) against the live index's report unless an explicit override input is given.

### 2. A new NuSEDS starts a run-timing workflow that rebuilds from the old kept copy and publishes nothing
Severity 3, wrong-or-missing-data, confirmed, reaches an angler; area forecast-runtiming. Related ticket: T485 (PARTIAL; step 3 open, does not name this).
- Evidence: app/workers/feeds/src/runtiming.ts:32 dispatches feeds-runtiming.yml with inputs { upload: "true" } only. Since T485 step 2 (cb20055c6), .github/workflows/feeds-runtiming.yml:127 fetches sources only when REFRESH is true (or no kept copy); otherwise it untars private/runtiming/src/sources.tar.gz. So the worker-started run parses the old NuSEDS, diff says "same files", step 7 is skipped and the run is green. dispatch.ts:49 then returns the recorded "started" for that version for ever, and dispatchSteps (dispatch.ts:79) emails "Nothing to press: the worker started ...". index.json sources.dfo.updated never moves.
- Example: Live timing.json: sources.dfo.updated = 20260601. When "All Areas NuSEDS_2027MMDD.zip" appears, the worker starts one run with refresh unset; the kept copy (max age 400 days) is rebuilt and nothing is uploaded.
- Second opinion: Nothing overstated. Two additions: BUTTON (runtiming.ts:11) also tells the owner to press with "upload: true" and no refresh, so the by-hand path has the same no-op; and the weekly check keeps finding latest > current but the version is already recorded as started, so nothing retries. Depends on the kept copy existing (T485 step 2 says its proof is the first run that keeps one); before that, every run fetches afresh.
- Proposed fix: Pass refresh: "true" in the worker's dispatch inputs (runtiming.ts:32), and have the workflow fail (or report loudly) when a refresh was the reason for the run and sources.dfo.updated is still older than the version that triggered it. Add a worker test asserting the inputs.

### 3. Decades-old DFO surveys replace the current PSF spawning curve, with no age gate
Severity 3, wrong-or-missing-data, confirmed, reaches an angler; area forecast-runtiming.
- Evidence: pipeline/runtiming/parse.py:188 takes `sorted(by[k])[-MAX_YEARS:]`: the latest 25 DATED survey years, however old, with only MIN_YEARS=3 as a gate. pipeline/runtiming/feed/bind.py:236-239 then drops that slot's PSF spawning runs on every section a DFO record is `observed` on. Survey age is only a tiebreak between sites (bind.py:197). The feed carries years [n, first, last] (build.py:101) and the tap sheet says "DFO surveys: 5 years, 1940-1948" (core/src/runTiming.ts:463), but the map paint and the watershed-group field treat it like a current run.
- Example: data/source/runtiming/timing.json: of 4,944 DFO records, 299 have their last dated survey before 1980, 884 before 1990, 2,300 (47%) before 2000. dfo:186:Sockeye:LATE (East Creek) is 5 surveys from 1940-1948, window Oct 25 - Nov 3. dfo:10:Chum:- (Hoy Creek) is timed from 1980-1993 while its counts run 1996-2012.
- Second opinion: The replacement itself is a recorded owner decision (bind.py:15-16, "owner 2026-10-24: DFO where it is better"), so the gap is the missing age rule, not the replace rule. Hoy Creek's 1996-2012 series is `adults` (NATURAL_ADULT_SPAWNERS); its `counts` is null. I did not measure how many of the old records actually bind and displace a PSF curve (needs the atlas base); the 47% is of parsed records, not of painted sections. The sheet does state the survey years (core/src/runTiming.ts:463), so it is disclosed on tap, not on the map.
- Proposed fix: Owner decision on an age rule: for example a DFO record replaces PSF spawning only when last_year is within N years, and older ones are either kept beside PSF as 'historic' or dropped. Report the count of records per age band in report.json so it is visible each build.

### 4. ArcGIS error bodies and zero-row answers are read as 'model out of season'; forecasts vanish with no failure recorded
Severity 3, fragility, confirmed, reaches an angler; area forecast-runtiming.
- Evidence: pipeline/gauges/feed/forecast.py:197-200 and app/workers/feeds/src/gauges/forecast.ts:104-107 both take `data.features ?? []` without looking for an `error` key; ArcGIS REST commonly answers HTTP 200 with {"error":{...}}. Zero rows is not an exception, so the model is not added to `failedModels` (forecast.ts:118-124) and the worker's last-good carry (publish.ts:575-581) does not run. Station files are rewritten without that model's runs, the index loses forecast/ahead/change for them, and health sees a clean run. Neither side compares the row count with the previous run's.
- Example: Recorded fixture day 2026-10-28: 325 CLEVER + 157 COFFEE + 369 ELF runs were live on 2026-10-22 (forecast.py:391 comment). A 200-with-error answer for CLM_MapHub_forecast would drop all CLEVER runs for that tick; stations then show COFFEE alone or ELF with the low-water caveat.
- Second opinion: That ArcGIS answers 200 with an error body is general ArcGIS behaviour; I did not see one recorded from these services in the repo, so the trigger is plausible, not observed. One thing the finder missed makes it worse: publish.ts:593 saves the forecast state whenever fcast is non-empty and nothing is in forecastFailed, so a zero-row model overwrites the last-good summary and the carry cannot bring it back on a later honest failure. The "hundreds of re-fetches" claim follows from station files losing the kept series but I did not trace withSeries to confirm the count.
- Proposed fix: Treat an `error` key, a non-array `features`, or a missing Station_ID/Issued_at column in the first row as a failed model (throw in query). Also treat a model that had N runs in the last forecast state and returns 0 on the same Centre day as failed, so the last-good carry applies and health records it.

### 5. Run timing is fetched once per app process and never again
Severity 3, wrong-or-missing-data, confirmed, reaches an angler; area deliver-contract.
- Evidence: app/packages/data/src/feed/runtiming.ts:86-89: `latest() { held ??= get(); return held; }` with no TTL and no refresh/offer; the source is created once (apps/mobile/src/App.tsx:242 `useMemo(..., [])`). Compare the siblings: salmon and in-season re-ask after 60 min (feed/salmon.ts:36 SALMON_FEED_TTL_MS, feed/inseason.ts:23) and take `offer`/`refresh` from the update service. `get()` returns null when the first ask is offline with no capture (runtiming.ts:57), and that null is latched too.
- Example: Open the Runs tab once with no signal on a fresh install: null is held; back in coverage the tab stays empty until the app is killed. A phone left running also keeps the capture labelled by its first read after the feed is republished.
- Second opinion: As stated. Added consequence: when a new release with another atlas is applied in the running app, the held run timing is still the old one, so the Runs tab reads 'stale' (ui/src/runTiming.ts:118) until the app restarts, even though the new index is on the origin. Run timing itself changes rarely, so the 'old data' half matters less than the latched null and the post-update stale state. T485 (PARTIAL) covers the publish side only, not this.
- Proposed fix: Give it the same TTL as the other feeds, never latch a failed/null read, and wire it into the update service (`refresh`) like in-season. One shared 'captured feed' helper for the three feeds would remove the three hand-written copies of this logic.

### 6. One mutable run-timing index for one atlas: a device on other tiles overwrites its working capture and loses run timing
Severity 2, fragility, confirmed, reaches an angler; area forecast-runtiming.
- Evidence: runtiming/index.json is the single mutable key and names one section_handles/tile_version (pipeline/runtiming/feed/__init__.py:29-31). deploy/staging/upload.sh:54,102 publishes it for the NEW tiles before the release pointer flips. In app/packages/data/src/feed/runtiming.ts:57-66 the app fetches the index, and when its files differ from the capture it downloads them and `store.write`s over the capture without checking the device's own tiles. app/packages/ui/src/runTiming.ts:109-118 then finds handles != facts.handles and reports "stale" (core/src/runTiming.ts:474: "Run timing is out of date for this map, so it isn't drawn").
- Example: A phone holding release A (handles hA) with a good hA capture opens Runs after release B's run timing is uploaded: it replaces the capture with hB data and draws nothing until it has taken release B, including later when offline.
- Second opinion: "Every device not yet on the newest tiles" is too wide: it bites only when the new release's section_handles differ (the first part of the tiles id, i.e. an atlas change), and the device still holds the old tiles. For every device there is also a short window between the run-timing publish and the pointer flip in upload.sh. The loss is said on screen ("stale"), not silent; the avoidable part is the overwrite of a matching offline capture at runtiming.ts:68.
- Proposed fix: Key the index by handles (runtiming/<handles>/index.json, the old one left in place) and have the app ask for its own tiles' handles; at minimum, do not overwrite a capture whose handles match the device's tiles with one that does not.

### 7. Name keys outside the one pipeline name key (names.key): four more rules, one of which drops data silently
Severity 2, duplication, partly, reaches an angler; area cross-duplicates.
- Evidence: pipeline/common/names.py:59 is THE key (accents folded, apostrophes deleted, punctuation -> space). Other rules still live: pipeline/runtiming/feed/base.py:46 name_key (lower, apostrophe deleted, hyphens/periods/accents kept; drops ' - suffix'), used at base.py:145 and bind.py:186 where a non-match means `if not secs: continue` (bind.py:189). pipeline/regs/review/names.py:76 key (no accent fold; feeds candidate ids at :86). pipeline/regs/review/dfo_auto.py:37 _norm (unused). pipeline/regs/review/marks.py:1095 _norm (casefold + spaces only; decides 'same proposal' at :1115,:1125). pipeline/tools/audit/tidal_candidates.py:189 and tidal_preverify.py:70 (identical copies, no accent fold).
- Example: "Pend-d'Oreille River" vs "PEND D'OREILLE RIVER": names.key gives one key (its own docstring example); runtiming name_key gives "pend-doreille river" vs "pend doreille river", so the DFO site binds no section and is skipped without a report line.
- Second opinion: The duplication is real. The data-loss claim is unproven: the Pend-d'Oreille example is hypothetical and I found no real run-timing site lost to punctuation (not checked against NuSEDS data). 'Binds nothing' on a name mismatch is also the designed behaviour (bind.py:174, Esker Slough), and the report gives bound counts (bind.py:240), so a punctuation miss cannot be told from a designed one. This affects run-timing only, not regulations.
- Proposed fix: Make runtiming name_key = names.key(name.split(' - ')[0]); make marks._norm and the tidal audit keys call names.key; delete dfo_auto._norm; keep review/names.key only as a frozen id slug and rename it so. Report run-timing sites that bind nothing.

Severity 1, doc-drift, confirmed; area forecast-runtiming.
- Evidence: data/source/runtiming/timing.json is tracked (fetched 2026-10-28/29) and is what `feed.release --local` binds for the local test bed (pipeline/runtiming/feed/release.py:23,59-77). - Example: After a refresh=true workflow run, staging run timing is built from a newer NuSEDS than the tracked timing.json the local test bed and the age counts above are read from.
- Second opinion: Accurate, and low stakes: the tracked file feeds the local test bed only, so the served data is not affected. One more stale line in the same README: :18 says "every fetched file is gitignored", but run-timing.html, biological-status.html, catch-and-run-size.html and fetched.json under data/source/runtiming are tracked, which sits oddly with the rule that PSF pages are not re-hosted (workflow header :18-19, T162).
- Proposed fix: Have the refresh run write the parsed timing.json's source stamps (sources.*.updated/fetched) somewhere the repo checks against the tracked file (or stop tracking it and pull the kept copy for --local). Correct the three doc passages.
