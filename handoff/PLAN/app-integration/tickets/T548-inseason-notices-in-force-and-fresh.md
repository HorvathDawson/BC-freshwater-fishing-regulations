# T548 — In-season notices: a notice still in force is shown, the feed has a stale rule, and the app says it reads it

Status: OPEN.

Source: data pipeline review 2026-11-09 (owner-led; 14 areas + a gap check, every finding re-read against the code and release data by a second reviewer). Rank 4 of 17; highest severity 5 of 5.

Line numbers are the reviewers' and may be off by a few; "Second opinion" is what the verifier corrected. Fixes are proposals: re-read the code before building.

## Today
### 1. A notice with one printed seasonal window is hidden after that window's first year, while it is still in force
Severity 5, wrong-or-missing-data, confirmed, reaches an angler; area inseason.
- Evidence: app/packages/core/src/inseason.ts:117-127 (inSeasonSpan): when a row has no `to`, it invents one from `parsed.window` in the `from` YEAR only; joinInSeason:160 then drops the row once that day passes. The worker sets `window` whenever the change text prints exactly one date range (app/workers/feeds/src/inseason.ts:364-368). A recurring window ("August 15 to December 31") is read as a one-off end date. Same rule copied in pipeline/regs/inseason/matches.py:244-262. No curated `effective` override exists on any of the 32 matches. Confirmed against the captured feed data/generated/inseason/feed/index.json (fetched 2026-11-08).
- Example: is-8cd37f6e5bf9 Fraser River (R2), effective "September 16, 2025": "No fishing for steelhead downstream of Spuzzum Creek confluence ... August 15 to December 31." -> to=2025-12-31, so today (2026-11-09, inside the window) no banner. is-498820589328 Fraser (R5) "... January 1 to December 31" -> hidden since 2026-01-01. Both are matched to gnis:39325 and still on the Province's page. is-74fcb31b2d0b Heber Creek will vanish after 2027-08-31 though half its text is a year-round closure.
- Second opinion: Accurate. One nuance: the same inference also hides seven 2026 rows printed "July 30 to September 15" (Salmon, Okanagan, Similkameen, Granby, Bessette), which look like genuine one-off summer closures, so the inference is right for those; the fix must tell a recurring window from a one-off (or stop inferring and rely on the page dropping the row), not simply delete the rule without an owner look. That the Fraser rows are legally still in force rests on the Province still listing them, not on anything in the repo.
- Proposed fix: Never infer an end from a month-day window: a row is in effect until the page drops it or a printed/curated `to` passes. Use the window only to word the banner (or as a yearly-recurring hint). Fix both copies and add a test using these two real rows.

### 2. The in-season feed has no staleness verdict; code and words still say the app does not read it
Severity 4, missing-check, confirmed, reaches an angler; area inseason.
- Evidence: app/packages/core/src/staleness.ts:74-75 `inseason: { by: "notRead" }` ("not read by the app"); menu/freshness.ts:32-33 and more.ts:71,90,121 repeat it. The app has read the feed since T230 and keeps the last capture indefinitely (app/packages/data/src/feed/inseason.ts:28-36, 52). The only age shown is the water page's "in-season <ago>" (ui-native/src/WaterScreen.tsx:157 from feed.fetchedAt; core/menu/legal.ts:89), with no threshold. The worker rewrites the feed at least every 20 h (FEED_HEARTBEAT_MS, worker inseason.ts:223), so an age rule is possible, as T526 did for DFO.
- Example: T486: the staging feed stopped refreshing 11-06 and only the staging smoke noticed. On a device the same outage reads "in-season 3 d ago" in plain text, banners unchanged, sync dot and Data block silent about it.
- Second opinion: File path fix: the third site is app/packages/core/src/more.ts:121 (not menu/more.ts), plus menu/words.ts:121 which the finder did not name and is the user-facing false sentence. Slight overstatement: an HTTP failure or unparsable body IS reported and shown on the sync badge (data/src/feed/inseason.ts:38-40 comment, T368); what goes unflagged is a feed that answers 200 but has stopped being rewritten (worker blocked or failing) and a long-offline phone.
- Proposed fix: Give `inseason` an age rule like `dfo` (stale after about a day by `fetchedAt`), feed it into the sync dot / Data block, and word the water-page line as stale. Fix the "not read" comments and words. Also update the worker's stale texts (inseason.ts:5 and :214 "not in the app yet").

### 4. In-season feed: an unreadable index is silently replaced by the last capture (or nothing), and the update service still marks the feed as updated
Severity 3, wrong-or-missing-data, partly, reaches an angler; area app-update-integrity.
- Evidence: app/packages/data/src/feed/inseason.ts:49-52: `const feed = parseInSeasonFeed(f); if (!feed || ...) return was;` with no reportFailure. Only HTTP and JSON errors are reported (getJson :41-46), and unreadable links are reported (:55, T520), but not an unreadable feed. app/packages/core/src/inseason.ts:72-79 rejects the whole feed on a format mismatch or on one row missing id/water/change. app/apps/mobile/src/App.tsx:338: the service's apply for in-season is `() => inSeason.refresh?.()`, which never throws, so update/service.ts:342-344 records the feed as seen and changed with a new updatedAt.
- Example: Code trace: the worker publishes one row without `change`, or bumps the format (app/workers/feeds/src/inseason.ts:464 writes FEED_FORMAT). An older app shows the last captured notices, or "no in-season changes" on a fresh install, and the sync row reads as just updated with no error.
- Second opinion: The code path is real, but the 'one row without change' example cannot come from the current worker: it always writes string water/change/effective. The only reachable trigger today is a deliberate format bump, which would leave older apps on the last capture (or empty on a fresh install) with the sync row reading as updated and nothing reported. The kept copy does carry its own fetchedAt (WaterScreen.tsx:157), so it is not shown as fresh on the water page. Latent, not a live fault.
- Proposed fix: Give InSeasonSource an offer(text) like the salmon feed: parse in apply and throw when it is not a readable feed, so the service shows and reports it and does not mark it seen. In get(), call reportFailure when a body arrived but did not parse. Parse rows individually (drop and report a bad row) rather than rejecting the whole feed.

### 5. A posted in-season closure never changes the answer, the status or the map colour
Severity 3, wrong-or-missing-data, partly, reaches an angler; area inseason.
- Evidence: By design (T230, owner 2026-10-28): app/packages/core/src/inseason.ts:8-9 "INFORMATIONAL ONLY ... never changes a computed answer or a status"; app/packages/ui/src/inseason.ts:9 "nothing here touches an answer, a status or the map's colours"; the banner's note is inseason.ts:271 "the answers on this page do not include it yet". Since T472 the notice is one collapsed line above the species table (inSeasonSummary, inseason.ts:292-295). The worker already classifies rows (`parsed.kinds` includes `closure`, worker inseason.ts:346) but nothing reads it for status. No open ticket in the ledger covers it.
- Example: is-c77bf6cd7da6 Stave River, effective November 18, 2025, kinds=[closure]; is-6db43a66acf9 Peace River closure. The water's page still computes Open from the synopsis; the only sign is a collapsed "In-season change (since Nov 18, 2025) · see ›" line. Map and search show nothing.
- Second opinion: The facts are right, but this is a recorded owner decision (T230, T472), not a defect: it is a design question for the owner. Overstated: "map shows nothing" - the water page's map does highlight the covered sections (T518/T520, ui/src/inseason.ts:3-5); only the main map colour and status are untouched. The Stave example is really the Northrop Spawning Channel row (matched to a wsc: channel item, whole + tributaries), not the Stave River mainstem. `kinds` comes from a regex on "no fishing", which also fires on species-only closures (steelhead), so driving a status from it needs care.
- Proposed fix: Owner decision: for a matched row in effect whose kinds include `closure` (not rescind/clarification), set the page status to "Check" and mark the covered sections on the map, as core's own comment already suggests. At minimum do not collapse closure rows.

### 6. An effective cell with an open end loses its start date, so a future-dated notice shows at once
Severity 2, wrong-or-missing-data, confirmed, reaches an angler; area inseason.
- Evidence: app/workers/feeds/src/inseason.ts:332-340 (effectiveDates): the cell is split on to/-/–/until; with two parts, unless BOTH parse as dates the result is {from:null,to:null} (:337). So "April 1, 2027 until further notice" or "July 30 to September 15, 2026" (first part has no year) gives no `from` and no `to`. joinInSeason (core inseason.ts:160) treats a null `from` as already in effect. There is no flag or event for an effective cell that did not parse.
- Example: No such cell on today's page (all 32 rows parse a `from`); the path is in the code only. Today's formats: "July 4, 2025 to August 31, 2025", "Sept 16, 2025".
- Second opinion: Accurate as a latent code path; no row on the 2026-11-08 capture triggers it. The split also breaks a cell with three parts (falls to isoDate of the whole string, null). Direction is over-warning, and the verbatim `effective` text is not shown in the banner head, so the reader gets no dates at all.
- Proposed fix: Keep the parsed side when only one side reads (from = a when a parses). Emit an owner event when a non-empty effective cell yields no date, so it gets a curated `effective`.

### 7. A matched notice whose water id is not in the device's release is shown nowhere
Severity 2, wrong-or-missing-data, partly, reaches an angler; area inseason.
- Evidence: core inseason.ts:149-166 (joinInSeason): any row with a link goes to `matched`, never to the app-wide "not on the map yet" list. A page shows it only if `c.waters[page.item]` exists (ui/src/inseason.ts:108; core inseason.ts:225-226 returns null with no failure). The off-release failure (:236) fires only when the item IS found. Nothing checks that at least one of a notice's item ids exists on this device. publish.py:89-91 checks items only against LATEST.
- Example: Code path only (no live case found in today's data): links resolved on a newer release name a water that was re-keyed or added since the device's release (registry changes do re-key items, see the registry-change resync note). That notice is in `matched`, no page claims it, no report is sent.
- Second opinion: The code path is real, but no live case exists and the finder says so. Likelihood is low: item ids are gnis:/wsc: keys that survive ordinary releases, and of 456 water entries all are checked present on LATEST at publish. It needs a device a release behind AND a water added or re-keyed in between. Severity is minor until a re-key happens; note the reverse case (device release has the id, links name a newer release) is handled and reported.
- Proposed fix: When the links are off-release, treat a notice none of whose item ids the device's release knows as unmatched (listed app-wide) and report it once. Per-release links (previous finding) removes the case.

### 8. One matches.json for every release and app version: partial notices widen after each promote, and a format bump stops the feed
Severity 2, fragility, partly, reaches an angler; area inseason.
- Evidence: The links live at one key, feeds/inseason/matches.json (pipeline/deliver/sync_inputs.py:71), resolved on local LATEST only (publish.py:129-133). The app reads ranges only when links.release equals the device's release (core inseason.ts:155, 236); otherwise the notice is shown on the whole water and a failure is reported. The format constant exists twice (publish.py:42, core inseason.ts:25) with no parity test, only literals in each side's tests. The worker throws on any other format (worker inseason.ts:392-393), which fails the whole feed publish (:243-244); an older app keeps its captured links or none (data/src/feed/inseason.ts:55-57).
- Example: notice_waters.json holds 20 partly-covered water entries (e.g. Fraser "downstream of Spuzzum Creek"). After each staging promote, every device still on the previous release shows those on the whole Fraser until its data update is applied. The worker comment at :383 records that the /3 bump already left the worker behind once.
- Second opinion: Confirmed as designed, safe-direction behaviour (over-warning, reported). Overstated: the constant is NOT duplicated between worker and app - the worker imports core's INSEASON_LINKS_FORMAT (worker inseason.ts:16), so only Python vs TS is unpinned, and a mismatch is loud on both sides (worker run fails on the status page; app reports and keeps captured links, data/src/feed/inseason.ts:55-57), not silent. "Older app versions lose placement for good" only applies to a device with no captured links. The real residual cost is the wrong (whole-water) extent on devices one release behind, and a frozen feed during a format bump that nothing calls stale (see the staleness finding).
- Proposed fix: Publish the links per release (matches-<release>.json, keep the previous one) and let the app ask for its own release's file. Add a test that reads publish.FORMAT and compares it to INSEASON_LINKS_FORMAT (or generate one from the other).

### 10. Production links are checked against the Mac's LATEST, not the release production serves
Severity 2, fragility, partly, reaches an angler; area inseason. Related ticket: T537 (staging order only; the prod check is not covered).
- Evidence: deploy/prod/upload.sh:32 takes `REL=${REL:-$(cat data/release/LATEST)}` and :83 calls deploy/prod/sync-inputs.sh, which stages through sync_inputs -> publish; publish.py:129-133 only compares the matches' release with local data/release/LATEST. Nothing compares it with REL or with the bucket's release pointer. The prod script has no lock and no re-resolve step (staging has both: deploy/staging/sync-inputs.sh:27-45). A match saved in the review app is synced to staging only (staging script header); prod waits for a manual run.
- Example: Latent (prod is not live yet): staging promoted to a newer release than prod, then `REL=<older> deploy/prod/upload.sh` or a prod sync-inputs run on its own puts links naming the staging release into prod; every prod device is then off-release for all 20 partial entries.
- Second opinion: The finder's main example is wrong: `REL=<older> deploy/prod/upload.sh` after staging moved on is refused at upload.sh:37-41 (REL must be the release staging serves). What remains: (a) a prod sync-inputs run on its own while prod still serves an older release than LATEST, and (b) upload.sh when local LATEST has been promoted past what staging serves (REL given explicitly) - both put links naming LATEST into a bucket serving another release, with no refusal. Latent (prod not live), over-warning direction. T537 covers the staging order only.
- Proposed fix: In deploy/prod/sync-inputs.sh, read the bucket's release pointer and refuse unless matches.json names it (or pass --side-release for REL). T537 touches the staging order only; extend it or add a prod check.
