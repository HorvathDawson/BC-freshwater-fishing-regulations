### 1. Proposal ids collide (target slug cut at 70 chars): only one of several DFO marks lands per apply, the rest are reported "saved"
Severity 3, wrong-or-missing-data, confirmed, reaches an angler; area review-data-flow.
- Evidence: pipeline/regs/review/proposals.py:987 builds the proposal id as "mark-"+slug(scope)+"-"+_slug(m.target, 70); slug (pipeline/common/split_ids.py:20) lowercases, folds punctuation to "_" and truncates, so the "~2"/"~3" suffix of a long DFO location id is cut off. pipeline/regs/review/apply_proposals.py:94 skips any proposal whose id is in `tried`, :158 adds the id after the first one, :91 and :207 key dicts by id. The skipped marks produce no event, and curation-review/backend/write_through.py:169 turns "key not named in any event" into state "saved". Nothing is logged (write-through.jsonl only records refusals, :185).
- Example: Live now: marks.jsonl lines 2500-2503 (group save 2026-11-09 14:08). Commits 0dca85f24 (…fishing-boun~3) and 0c983cc9c (…upstream…fis~2) landed; `…from-a-line-between-2-fishing-boun` and `…boun~2` still hold 1 extent piece in data/curated/dfo_salmon/places/region-2.json while their marks in force say 2 (the Sumas River below Barrow Town Pump Station piece is missing). `apply dfo entries --dry-run` today prints one "would apply" for that shared id; the ~2 one is hidden behind it. 2 colliding ids cover 5 of 352 places, both groups have 2+ proposing marks in force.
- Second opinion: Mechanism and live example are right. Overstated impact: both unlanded places are status "dormant" with duplicate_of = the active `...boun~3`, which did land with both pieces, so no angler sees a wrong extent today; it bites only if a dormant wording revives or a collision hits an active place. I did not run the dry-run myself (no command run); the unlanded state is shown by the file contents. Entry/rule id collision is a risk only: 1 entry/rule mark proposes today, no collision found. The ~N suffix is cut because the id is exactly over 70 chars after slugging; shorter DFO ids keep `_2` and stay distinct.
- Proposed fix: Make the proposal id injective: keep the full target (or append a short hash of scope|target|rule_id when the slug was truncated or altered). Make apply_proposals refuse duplicate ids in one build (raise). In write_through._run, a mark with a proposing field (extent_fix, new_splits, variant_of, call) that no event names must be "unknown/not landed", not "saved". Then rerun apply for the two Chilliwack wordings.

### 2. No build/release gate checks that every mark in force has landed in its curated file
Severity 3, missing-check, confirmed, reaches an angler; area review-data-flow.
- Evidence: Builds read only the curated files (pipeline/regs/review/export.py:21-22; pipeline/build.py:51 is prose only). grep of pipeline/build.py, pipeline/deliver, scripts and .github for review.apply / apply_proposals / tidal_limits / mined_names --check finds no call. Only sloughs have a parity test (pipeline/tests/test_slough_fold.py:199-203); tidal_limits.json and found_names.json have a `--check` CLI (pipeline/tools/tidal_limits.py:149, mined_names.py:92) that nothing runs; there is no check at all that `apply dfo entries --dry-run` is empty. Write-through outcomes (refused / waiting) live in process memory (write_through.py:66-67) and are gone after a review-app restart.
- Example: Today the three file checks pass (I ran them: slough_calls current, found_names current, tidal current), but `python -m pipeline.regs.review.apply dfo entries --dry-run` reports an applicable, unlanded proposal for 2:chilliwack-vedder-river-including:from-a-line-between-2-fishing-boun, and build 24 / the next release would ship without anyone being told.
- Second opinion: Line refs slightly off (outcomes dicts are :70-71, not :66-67). The finder's dry-run output and "three checks pass today" were not re-run by me; the unlanded Chilliwack marks are confirmed from region-2.json vs marks 2501/2502 (both dormant duplicates, so the next release is not wrong because of them). `waiting` is by design for cut-changing proposals awaiting a side rebuild, so a gate needs the allow-list the finder proposes or it will fail routinely.
- Proposed fix: One read-only command (e.g. `review.apply --check`): runs the three file writers in memory and compares to disk, runs apply_proposals --dry-run and fails on any would/refused/waiting event that is not on an explicit, dated allow-list. Call it from the release script and the fast test lane; print the list in the review app on start-up.

### 3. No gate checks that review marks are applied to the three write-through files, and the by-hand writers bypass the T429 guard
Severity 2, missing-check, partly, reaches an angler; area static-layers. Related ticket: T429 (DONE; shrink guard only on apply.write_files, not the three tools' main()).
- Evidence: Each writer has a --check (pipeline/tools/tidal_limits.py:152-155, slough_calls.py:104-108, mined_names.py:109-112) but nothing calls it: no hit for these modules in scripts/, .github/ or pipeline/release.py; release preflight explicitly lets marks.jsonl be dirty (pipeline/release.py:330, 558). Two write paths differ: apply.write_files is atomic with shrink_refusal (apply.py:93-124); slough_calls.main (line 109) and mined_names.main (line 113) use plain write_text with no shrink guard, and mined_names --check reads with the locale encoding. The files' own ABOUT/error text tells people to run the unguarded command (slough_calls.py:86).
- Example: Both checks report current today (`mined_names --check`, `slough_calls --check` run read-only 2026-11-09), so this is a gap, not a present fault.
- Second opinion: "Nothing calls it" is wrong for sloughs: pipeline/tests/test_slough_fold.py:196-202 (test_the_committed_file_is_apply_of_the_marks) asserts slough_calls.json == SC.document(build(E.load())) against the real marks, though only in the full suite (smoke.txt lists a different test of that file). No equivalent test exists for tidal_limits.json or found_names.json, so the gap is real for those two. Only two of the three by-hand writers are non-atomic; tidal is atomic. Write-through failures are also said on the item, not only logged.
- Proposed fix: Add `python -m pipeline.regs.review.apply --dry-run` (must report every file domain current) to fast-fail and to release preflight. Make the three tools' main() call apply.write_files so there is one write path (atomic, shrink guard, utf-8).

### 4. Mark-derived curated files are rewritten whole from marks x current candidate files; up to 10 rows can vanish per save, silently for names
Severity 2, fragility, partly, reaches an angler; area review-data-flow. Related ticket: T429 (DONE) added only the >10 rows guard.
- Evidence: pipeline/regs/review/apply.py:113-128 rewrites the full file on each save and only refuses a drop of more than SHRINK_LIMIT=10 rows (:87). pipeline/tools/mined_names.py:33-36 drops an accepted name when its candidate's prints moved (`continue`, no skipped list, no event); build() :47-64 also depends on candidates.json `auto_accept_eligible`. pipeline/tools/slough_calls.py:47-53 drops gone/stale candidates (reported as refused events, file still written). pipeline/tools/tidal_limits.py:55-58 swallows SystemExit from T.load into `existing = []`, and rows depend on the live atlas line starts (:66) and tidal candidates (:71).
- Example: found_names.json holds 184 entries while marks.jsonl has 0 name marks: every entry comes from data/generated/review/name-variants/candidates.json + found_name_calls.json, so regenerating candidates changes a curated build input on the next Names-tab click; 1-10 names lost would pass the shrink guard with no message.
- Second opinion: The up-to-10 silent drop for names is real, and since there are 0 name marks every one of the 184 entries is derived from generated candidates + found_name_calls.json, so a candidates regeneration can change a curated build input on the next names apply. Overstated: (1) with 0 name marks the review app never runs the names writer on a save today (write-through runs only the saved mark's domain), so the trigger is a manual `review.apply`/`mined_names` run; (2) sloughs and tidal drops are reported per item as refused/waiting events, not silent; (3) the tidal SystemExit swallow would lose owner hand rows only if the file is missing, and the >10 guard would then usually refuse the write. Any change also shows in git diff since the writer says "commit it". Effect is a missing name alias/slough fold, not a wrong regulation.
- Proposed fix: Writers return a `dropped` list (rows on disk that the new text lacks) and apply.write_files refuses ANY unexplained drop unless the saved mark's own target explains it (un-mark/reject); report names' stale rows as events like sloughs do; replace `except SystemExit` with a real missing-file branch.

### 5. Every apply re-asserts all marks in force against the files; the 'extent changed since the mark' guard covers 4 of 93 DFO fix marks and no entry/rule mark
Severity 2, fragility, partly; area review-data-flow. Related ticket: T525 (IN REVIEW) covers the guard for new DFO saves only.
- Evidence: pipeline/regs/review/proposals.py:883 takes every in-force mark that proposes; :1046-1070 emit an edit whenever the file's field differs from the mark's value, with no staleness or date test. The only guard is `extent_before` (:1071-1079, T525), DFO only and only on marks that carry it; the catalogue branch (:1080-1097) has none. apply_proposals then commits each one (apply_proposals.py:186) on the next save of ANY mark in the domain (write_through.py:149 runs the whole domain).
- Example: marks.jsonl in force: 93 DFO marks with extent_fix, 4 with extent_before (lines 2500-2503); 0 entry marks carry a guard. Consequence already visible: the T523 cut-id rename (commit 1d58354b3) had to edit a marks.jsonl line in place (numstat 5 added / 1 removed) although data/curated/review/README.md:5 says the store is "APPEND-ONLY, never edited by hand or by a tool".
- Second opinion: Code facts are right, but re-asserting is the stated design, not an accident: apply_proposals.py:9-15 says the marks are the decisions and to change one the owner changes the mark; curated place extents are meant to be mark outputs. So "a hand fix is silently reverted" is the intended contract, and the revert is a visible commit with a binding check, not silent. The in-place marks.jsonl edit was an owner-approved exception (surgical, diff-proven id renames), so it is doc drift plus a missing supported rename path, not a violated guard. Real residual risk: tool-driven renames/re-ingests of a marked place, and line-hash provenance changing when a line is rewritten. Entry/rule exposure is 1 mark today.
- Proposed fix: Record on landing what the mark replaced (extent_before for every proposing mark, backfilled for the 89 old DFO marks from the commit that landed them), and hold instead of re-landing when the file is neither the mark's before nor its after. Add a supported rename path (carry-style appended mark for renamed split ids) so the store never needs editing, plus a test that HEAD's marks.jsonl only ever grows.

### 6. found_names.json (curated, shipped names) is recomputed from a generated candidates file's auto-accept flag; a re-mine silently changes it
Severity 2, fragility, partly, reaches an angler; area static-layers.
- Evidence: pipeline/tools/mined_names.py:47-72 build(): iterates the CURRENT candidates (N.load, pipeline/regs/review/names.py:30 CANDIDATES = GENERATED.review/name-variants/candidates.json) and accepts every row with `auto_accept_eligible` (line 63-64) with no mark and no stored id. That flag is computed by handoff/PLAN/curation-review/name-variants/mine.py:651 (a script outside pipeline/). decisions() lines 33-36 drops a marked row whose candidate is gone or changed with `continue`, no report (the slough writer reports the same case as skipped). The only guard is apply.SHRINK_LIMIT=10 (pipeline/regs/review/apply.py:86); additions are unlimited.
- Example: data/curated/waters/found_names.json today: 189 of 197 name records carry accepted = "owner 2026-10-29: accepted (auto rule, line coverage >= 80 %)"; only 8 come from an owner call. candidates.json holds 8,833 rows.
- Second opinion: Mechanism confirmed, "silently" is overstated: candidates.json is tracked in git (git ls-files) and nothing in build.py/release.py/scripts runs mine.py, so a re-mine is a hand run that shows as a diff in two committed files, and apply prints "wrote ... commit it". The real gap is that the accepted set is not frozen and a marked candidate that vanished is dropped with no report. Minor: the writer is at lines 41-65/94-98, not 47-72/109-113.
- Proposed fix: Freeze the accepted set: write the auto-accepted candidate ids (with the candidate's print) into found_name_calls.json once, and make mined_names accept only ids listed there or marked. A candidate that is listed but gone/changed is reported as skipped and fails --check. Move mine.py under pipeline/ and pin candidates.json's digest in the found_names header.

### 7. An accepted found name on a lake or a registry item is written but never applied; names on features not in the atlas are only a printed count
Severity 2, wrong-or-missing-data, confirmed, reaches an angler; area static-layers.
