# Owner decisions in force

One line per decision, by subject: what, the owner's date, the ticket. A decision a newer one replaced is deleted, not
struck out; the tickets and git hold the history. Verbatim words appear only where the wording is the decision.

- How the book is read (every interpretation ruling): `pipeline/docs/RULINGS.md`; it wins over this page.
- Working rules for agents (never run the parser, CONFIRM_PROD, commits, tests): `AGENTS.md`. Not repeated here.
- A "Claude" tag means the owner delegated the call and it stands until he says otherwise.
- Where two decisions could not be reconciled, the last section lists both for the owner to settle.

## 2. The backend answers; the app only reads

- Every regulation answer is generated by the pipeline; the app decodes, selects, groups and words it, and never decides a regulation. A screen that needs an answer the store lacks gets it added to the pipeline's answers and the release. Regulation logic in app code is a blocker. (owner 2026-10-21, T05)
- A cascade or rule resolved by the pipeline reaches the app and worker as a compact pre-resolved result; no TypeScript cascade logic. (owner 2026-11-02)
- One water screen whichever way you reach it (either map, search, a spot, a link, a step): same route, header, parts and section, differing only in which view is in front. Both maps' taps call the one `openWater`. (owner 2026-10-21, T71)
- One load path per screen: same output whether reached by refresh, tab, search, tap, step or pick. (owner 2026-11-03, T369)
- One water never shows differently by platform, path, quantity or day. (owner 2026-11-10, T580)
- No hidden fallbacks or silent callbacks: a failure that is shown is also reported (`reportFailure`). (owner 2026-11-03, T333)
- A screen never asserts a fact about the data; it asks. Assert whole composed strings. Detail: AGENTS 32-33.
- Anything the app cannot read or a feed could not supply is said, never guessed. Never invent an end date for an in-season notice. (owner 2026-11-20, T548)
- An in-season notice whose own text states its range ("No fishing July 30 to September 15") shows its banner from 2 weeks before the first day through the last, then not at all; one with no range shows until the Province drops it; a range whose year cannot be read is shown undated and reported. Banner only, but louder: the answer and the map colour stay the book's. In force it wears the page's warning amber with a caution mark (the pointer on the status line too); the 14 days before stay grey; a range that starts after its effective day is never dated. (owner 2026-11-25, 2026-11-26, T1167)
- "?" does not exist in the review: a row is right or wrong; unsure counts as wrong, and older wordings need a per-wording human tick. (owner 2026-11-09, T532)
- Python decides every word, number and date; the app only draws. Where the data can be made right, change it all the way in Python so the front end needs no workaround. (owner 2026-11-16, T810)
- Simplify wherever a limit already implies another: drop the implied line and say the implication once, everywhere; the overall limit is still stated. (owner 2026-11-18, T810)
- The release gate: the build lists every DFO place whose latest owner save is "wrong" (no fix drawn) and refuses to ship until each is fixed and re-saved; a feed row that matches a stream but has no place yet puts DFO's words in the DFO rule section with the check style. (owner 2026-11-17, T786)
- Crashes carry the open water's id and pane state, and the privacy page says so. (owner 2026-11-03, T352)
- No old-link support: only the current link form is read. (owner 2026-11-03, T369)
- A menu or screen design the owner said is "Claude's choice" is built without asking and checked by the owner on the phone. (owner 2026-11-06, T453)

## 4. Waters, names and curation

- A water's kind follows the book (a slough or canal is a stream); the registry decides it once. Detail: AGENTS 55, RULINGS K1.
- Never show a digits-only name when the water has a lettered one; a number with a letter ("#14A") counts too. The number stays a search name. (owner 2026-11-20, T926)
- All name variants are searchable, no abbreviations and no numbered-lake names; no outside names source. (owner 2026-11-19, T926, T927)
- An accepted mined name is searchable and, on a water with no official name, is the shown name, labelled with its real source; only BC Geographical Names is official. (owner 2026-10-28, T224)
- Names are shown as sourced: nothing is dropped, renamed or filtered (no offensive-term list). (owner 2026-10-28)
- A name from a gauge is accepted when the station's own name plainly names the water, and credited to that gauge. (owner 2026-10-29, T224)
- A name clean-up lands only with a dry-run proof that every book row still matches the same water and no override JSON changes. (owner 2026-11-20, T926)
- "See X" group rows are pointers: member lakes show their rules under their own names; the group name leads to them. Main Lake also applies to Mine Lake. (owner 2026-10-22, T80)
- A typed id an override pins resolves to every lake item whose own polygon carries it (Twin Lakes). (owner 2026-10-22, T89)
- The Okanagan River oxbows are all streams, still bound by their book exemption. (owner 2026-10-24, T55)
- Sloughs and canals follow their water's kind: a polygon of a stream item colours and gets gauges as the stream, even polygon-only. (owner 2026-10-22, T55)
- Ponds: a pond is a lake by default; the pond domain is closed and nothing is exported for it. (owner 2026-10-30, T329)
- Waters printed in an MU holding no registry water of that name stay unbound and listed; a same-name water elsewhere is never bound. (owner 2026-10-23, T89)
- A lake never answers to its through-river unless the book names it; a creek-fed loop stays with its river. (owner 2026-11-15, T743)
- Different rules on the two sides of a lake: separate pieces; the same rules: one part across any lake, named or not; one part per connected adjacent stretch. (owner 2026-11-08, T517)
- A river's pieces (side loops, same-lake loops) are taken out of the river and given to the lake where they belong; the water map walks upstream/downstream along one line through every part, ranked by the upper end. (owner 2026-11-14 / 2026-11-15, T750, T753)
- A lake divided into closure areas (a lake split) is deferred, not curated; its only issue marks it "later" in review. (owner 2026-10-28)
- A continuation link ships only when listed `reviewed` in `continuations.json`; the atlas only proposes. (owner 2026-10-29)
- A river that changes its name (Vedder/Chilliwack, Bella Coola/Atnarko) is one system for back and for its own gauge. (owner 2026-10-22, T76)
- The curated list of owner marks is the owner's: marks only ever append; a saved mark writes through to its curated file; no manual lock. (owner 2026-10-30, T325)
- Reviewers mark only; there is no fix mode; marks are the owner's decisions and Claude applies them one commit each with a binding check; everything Claude adds for review lands as a proposal, never pre-accepted. (owner 2026-10-24 / 2026-10-27 / 2026-10-29, T185)

- The name normaliser and similar one-time repairs may be promoted by Claude when the binding diff shows only explained changes. (owner 2026-10-24, T61)
- A bulk reclassification runs a dry run and is confirmed before sweeping; tight filters only. (owner 2026-10-24)
- Deleting a curated cut is never done: every curated cut was added for a reason; find the rule or DFO scope that uses it, or show it as an open high-severity item. (owner 2026-10-26, T207)

## 6. Gauges and flow

- Flow leads; Level is auxiliary. One lead gauge per water and day is chosen in Flow; Level never picks its own. The estimate card stays on Flow whatever the gauge card shows. Never mix flow and level quantities. (owner 2026-10-22 / 2026-11-10, T581, T971)
- A water's own gauge carries the main weight in the quantity it measures; other donors are auxiliary with a smaller share; the own gauge stops leading only when it is far from the tapped spot or its catchment is far smaller. Constants (lead share 0.7, ratio 10, far fraction 0.2, floor 10 km, area trust 10) are kept. (owner 2026-10-22, T76)
- A gauge on a continuation (`water_continue`) counts as the water's own; a tributary, side channel or receiving river does not. The walk along the water is ended by a named lake but passes unnamed ponds that belong to no water. (owner 2026-11-20, T679)
- A gauge across a continuation link applies only where its drainage is a large share (>= 0.5) of the reach's. (owner 2026-10-28, T93)
- A side channel follows its own river's gauge; where its own river is silent it is silent. A side-channel gauge never answers Level for the river it branched from and answers Flow only where it carries a large share (0.5). (owner 2026-10-22 / 2026-10-23, T101)
- WSC code decides parent/child in the tributary walk; Strahler order only breaks ties. (owner 2026-10-23, T102)
- Estimates use every station with a usable record that could inform the section, chosen at read time among those reporting now and renormalised; a station joining or leaving the roster changes estimates with no rebuild. (owner 2026-10-22)
- A gauge whose route to the water crosses a lake keeps 5% of its weight and may not lead whenever another reporting gauge reaches without a lake; if all cross a lake the panel says "Measured below Pitt Lake: the lake smooths changes, so read it loosely." The map matches the click; the pipeline ships the fact, never the weight. (owner 2026-10-29, T296)

## 12. Data flow (owner walkthrough 2026-11-05, T408; the map is `docs/data-flow.md`)

- A review mark makes one hop: appended to `marks.jsonl`, written through to its final curated file; no middle `decided/` copy. The build reads only final files. (owner 2026-11-05, T325)
- Curated holds only the owner's decisions and the files the build reads: machine output and proposals live in `data/generated/` (gauge candidates, `review/dfo_fix_proposals.json`), and the app reads proposals there. (owner 2026-11-05, T324)
- Hand-edited waters files stay hand-edited, with a fast schema-and-reference check as the build's first step. (owner 2026-11-05, T324)
- Accepting a regenerated steelhead list is a decision: one command prints the diff (added, dropped) and writes the curated file. (owner 2026-11-05)
- Every build checks each saved DFO match id still exists in that build's registry and fails otherwise; a new DFO name with no match is held unplaced and a human matches it. (owner 2026-11-05, T337)
- The worker has one copy of the DFO wording (R2); missing or invalid fails the job and reports, the app keeps the last good feed. (owner 2026-11-05, T324)
- Run timing is a slow feed: its own R2 folder and `index.json`, started by a button or the worker, never a GitHub schedule. (owner 2026-11-05, T413)
- One command ships, "build once, promote the same artifact": `pipeline release --staging` = build, checks, promote LATEST, staging upload, stop at the first failure. The same command is the human's; a short runbook. (owner 2026-11-05, T408)
- Claude batches rebuilds after curated changes (one build via `heavy.sh`, diff summarized). (owner 2026-11-05)
- Curated file names are accurate and consistent: `*_calls.json` per-item decisions, `*_waters.json` lists of waters, `*_stations.json` lists of gauges; every JSON keeps an `_about` header and every curated folder a README. (owner 2026-11-05)
